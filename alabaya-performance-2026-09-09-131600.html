1. Executive Summary

Alabaya is an iBilling-based PHP 7.4 invoicing and ERP application (Smarty + Idiorm/ORM, MySQL). Source review found several high-impact query and frontend patterns that will scale poorly as invoices, stock movements, and contacts grow. No production outage was confirmed. The highest-risk issues are N+1 GST reporting, about 88 extra SUM queries on dashboard charts, DATE()-wrapped P&L filters, per-product stock lookups in the invoice item modal, and loading entire timesheet result sets into PHP to compute a total.

Invoice list, contact list, and product list DataTables already use server-side pagination with aggregated stock SQL. Those are positive patterns and should be kept. The remaining hotspots are unbounded catalog loads, “Show all” DataTables options, duplicate bootstrap queries, disabled OPcache/gzip on this XAMPP host, and no application query cache.

7. Backend Performance

PHP bootstrap starts a file session, configures Idiorm, loads language files and plugins, then includes the controller. Controllers are large: invoices.php is 4963 lines, contacts.php 2742, transactions.php 1553. Invoice add/edit loads all sys_items, sys_cloths, and sys_designs. Transaction add (transactions/a) loads all crm_accounts for a dropdown. Employee timesheet DataTables first find_many() every matching row to sum earnings, then runs a second paginated query. Cron complete-order notifications call WATI HTTP sequentially with CURLOPT_TIMEOUT = 0. Idiorm caching is off. Smarty has a compile directory but no output cache.

8. API Performance

JSON DataTables endpoints exist for invoices, products, transactions, contacts, and P&L. They are the right shape (server-side), but several honor DataTables length = -1 (“All”), which skips LIMIT and can return the full table. Dashboard JSON chart endpoints are chatty (many SUMs). Public WATI catalog endpoints send Cache-Control: no-store. Payload sizes and latencies were not measured.

9. Frontend Performance

Admin layout loads jQuery 1.10.2 and jQuery UI in <head> without defer/async, plus many CSS files, Line Awesome from a third-party CDN, and 12+ apple-touch icons. The footer always loads DataTables from cdn.datatables.net plus JSZip, even on pages that also load local datatables.min. Dashboard additionally loads full echarts.min.js. The invoice product modal sets DataTables pageLength: 5000 and paging: false, and each row calls product_stock_info() (two stock queries + PHP loops). No image lazy-loading was found in theme templates. LCP/INP/CLS were not measured.

10. Server Performance

This XAMPP php.ini has OPcache settings commented out and no zend_extension for OPcache. zlib.output_compression=Off. Apache mod_deflate and mod_expires are commented out. PHP memory_limit=2048M and max_execution_time=3600 locally (production-shaped project php.ini uses 256M / 30s). CPU, RAM, and MySQL buffer pool were not sampled. Production may differ from this laptop XAMPP stack.

11. Detailed Findings

N1-001 — GST reports load every invoice with nested item and tax queries

High Priority: P1

CategoryN+1 / unbounded query
Affected Areaapplication/controllers/reports.php cases gst-reports and gst-reports-ajax

Evidence

gst-reports runs ORM::for_table('sys_invoices')->find_many() with no date filter or LIMIT. For each invoice it loads all sys_invoiceitems, and for each item it find_ones sys_tax. The AJAX variant still loops invoices in the selected date range the same way.

Current Behavior

Query count grows as invoices × line items. All invoices are held in PHP memory for the initial page.

Root Cause

GST totals are computed in PHP instead of a joined SQL aggregation. Tax rows are fetched per line instead of once.

Recommended Fix

One query joining invoices, items, and tax, grouped by invoice. Cache tax types in a map. Paginate or require a date range on the initial page.

Example Fix

SELECT inv.id, inv.invoicenum,
  SUM(CASE WHEN tax.taxtype = 'GST' THEN ii.taxamount ELSE 0 END) AS gst_amount,
  SUM(CASE WHEN tax.taxtype <> 'GST' THEN ii.taxamount ELSE 0 END) AS igst_amount
FROM sys_invoices inv
LEFT JOIN sys_invoiceitems ii ON ii.invoiceid = inv.id
LEFT JOIN sys_tax tax ON tax.id = ii.tax_id
WHERE inv.date BETWEEN ? AND ?
GROUP BY inv.id;

Expected Improvement

Estimate: from O(invoices × items) queries to 1 query. Large GST pages should drop from multi-second to well under 1s if indexes exist. Not measured.

Tradeoffs

Need to match current CGST/SGST split rules exactly.

Verification

Enable Idiorm logging, open GST reports, compare query count and duration before/after. EXPLAIN the new SQL.

SQL-001 — Dashboard charts issue ~88 per-day / per-month SUM queries

High Priority: P1

CategorySQL / chatty ORM
Affected Areaui/lib/dashboard/dashboard.js, application/autoload/Dashboard.php, dashboard.php canvas + legacy

Evidence

On load, dashboard.js calls dashboard/json_income_vs_exp/, json_d_inc_exp_month/, and json_d_chart_data/. dataLastTwelveMonthsIncExp() loops 12 months × income and expense SUM. dataIncExpD() runs separate SUMs for each calendar day 01–31 for income and expense. Canvas also duplicates SUM(balance) for tbal and net_worth. Legacy dashboard uses filter_by_branch('sys_transactions') dozens of times (68 matches in dashboard.php).

Current Behavior

After HTML render, the browser triggers ~88 extra aggregate queries against sys_transactions.

Root Cause

Aggregates are computed in PHP loops instead of GROUP BY YEAR/MONTH or GROUP BY date.

Recommended Fix

Replace with two SQL statements (or one with conditional SUM). Reuse one SUM(balance) on the page.

Example Fix

SELECT DATE(`date`) AS d, type, SUM(cr) AS credit, SUM(dr) AS debit
FROM sys_transactions
WHERE `date` BETWEEN ? AND ?
GROUP BY DATE(`date`), type;

If date is already a DATE column, drop DATE() and group by date.

Expected Improvement

Estimate: 88 queries → 1–2. Chart TTFB should fall sharply on large transaction tables. Not measured.

Tradeoffs

Must preserve empty days as 0.00 for the chart.

Verification

Log queries for one dashboard load. Compare count and total DB time.

SQL-002 — P&L report repeats a full invoice-item GROUP BY and uses DATE() on a datetime column

High Priority: P1

CategorySQL / sargability
Affected Areareports.php case pl-products-dt

Evidence

$mainSQL left-joins a subquery that groups all sys_invoiceitems by invoice and another that groups invoice_alocation. That SQL is executed three times (count, page, totals). Date filter is DATE(inv.created_at_datetime) BETWEEN ? AND ?, which prevents a range index on created_at_datetime.

Current Behavior

Each DataTables draw can scan items and allocations three times.

Root Cause

Derived-table reuse via string concatenation; function wrapped around the date column.

Recommended Fix

Use created_at_datetime >= start AND created_at_datetime < start+1 day. Compute count/totals from one pass or a temporary table. Consider persisted COGS/expense on paid invoices.

Example Fix

AND inv.created_at_datetime >= ?
AND inv.created_at_datetime < DATE_ADD(?, INTERVAL 1 DAY)

Expected Improvement

Estimate: large date ranges should avoid full item scans three times; indexable date range. Not measured.

Tradeoffs

Confirm timezone/date-only semantics of created_at_datetime.

Verification

EXPLAIN before/after. Time a wide date-range draw.

N1-002 — Invoice product modal loads all products and queries stock twice per row

High Priority: P1

CategoryN+1 / frontend dataset
Affected Areaps.php modal-list, product-modal-list-ps.tpl, product_stock_info() in ibilling_misc.php

Evidence

Modal loads all customize and readymade sys_items. Template calls product_stock_info($ds['id']) per row. That helper loads all credit rows and all debit rows for the item, then sums in PHP. DataTables is configured with pageLength: 5000 and paging: false.

Current Behavior

Opening the product picker on invoice add/edit runs 2N stock queries and renders the full catalog in the DOM.

Root Cause

Stock is not joined; UI disables paging. (The product list page already solved this with aggregated SQL.)

Recommended Fix

Reuse the p-list-datatable aggregation. Server-side search. Restore paging (25–50).

Example Fix

SELECT i.id, i.name, i.sales_price, COALESCE(st.current_stock,0) AS current_stock
FROM sys_items i
LEFT JOIN ( /* same stock SUM as p-list-datatable */ ) st ON st.item_id = i.id
WHERE i.product_type = ?
LIMIT 50 OFFSET ?;

Expected Improvement

Estimate: modal open from 2N+2 queries to 1 paginated query; much smaller HTML. Not measured.

Tradeoffs

Users must search instead of seeing every SKU at once.

Verification

Open invoice add → product modal. Compare query count and HTML size.

BACKEND-001 — Timesheet DataTables loads every matching row into PHP to compute a total

High Priority: P1

CategoryLarge dataset / duplicate query
Affected Areacontacts.php timesheet employee JSON (~lines 540–623)

Evidence

After applying filters, $Records = $recordQuery->find_many() loads the full result. PHP sums earn_amount. A second query with OFFSET/LIMIT then loads the page.

Current Behavior

Memory and time grow with timesheet history even when the grid shows 10 rows.

Root Cause

Totals implemented as “load all then sum” instead of SUM(earn_amount).

Recommended Fix

Run COUNT(*) and SUM(earn_amount) on the filtered query; fetch only the page.

Example Fix

$totalFiltered = (clone $query)->count();
$earnAmountSumTotal = (clone $query)->sum('crm_timesheet.earn_amount');
$records = $query->offset($start)->limit($rowperpage)->find_many();

Expected Improvement

Estimate: large employee histories drop from loading thousands of ORM objects to one page + two aggregates. Not measured.

Tradeoffs

Unique invoice-number list for salary description may need a separate limited query or a truncated string.

Verification

Filter a long date range; compare memory and query count.

FRONTEND-001 — Global layout loads render-blocking scripts and duplicate DataTables

High Priority: P1

CategoryFrontend / critical path
Affected Areaheader_default.tpl, footer_default.tpl

Evidence

Head includes jQuery 1.10.2 and jQuery UI before body content. Footer always loads DataTables CSS/JS from cdn.datatables.net, buttons, JSZip, plus local copies on list pages via Asset::js. Line Awesome is loaded from icons8 CDN. Many favicon/apple-touch links. Scripts have no defer/async.

Current Behavior

Every admin page pays for DataTables and extra CDN RTTs, including pages that do not use a grid. Duplicate DataTables can inflate JS work.

Root Cause

Assets are global rather than page-scoped. CDN and local bundles overlap.

Recommended Fix

Move jQuery to the end of body or use defer. Load DataTables only on list pages. Pick one copy (local, versioned). Self-host Line Awesome or drop it if Font Awesome is enough. Reduce icon links to one favicon.

Example Fix

{if isset($use_datatables) && $use_datatables}
  <script src="{$app_url}ui/lib/datatables.min.js"></script>
{/if}

Expected Improvement

Estimate: fewer bytes and fewer connections on most pages; better FCP/LCP. Not measured.

Tradeoffs

Templates that rely on global DataTables must opt in.

Verification

DevTools network on login, dashboard, invoice list: script count, transfer size, TTFB.

SERVER-001 — OPcache and HTTP compression/expires are disabled on this host

High Priority: P1

CategoryServer / PHP
Affected AreaXAMPP php.ini, httpd.conf; project-root cPanel php.ini

Evidence

OPcache keys are commented; no zend_extension for OPcache. zlib.output_compression=Off. Apache deflate_module and expires_module are commented out. Project php.ini also has compression off.

Current Behavior

PHP recompiles scripts every request. Static assets are uncompressed and uncached by the server config reviewed here.

Root Cause

Default/dev XAMPP and a production ini without compression.

Recommended Fix

Enable OPcache in production (opcache.enable=1, adequate memory, validate_timestamps=0 after deploy). Enable gzip/brotli and long-cache headers for versioned CSS/JS.

Example Fix

zend_extension=opcache
opcache.enable=1
opcache.memory_consumption=128
opcache.max_accelerated_files=10000

Expected Improvement

Estimate: typical PHP apps see large TTFB gains from OPcache; gzip often cuts text assets 60–80%. Not measured here.

Tradeoffs

Must restart PHP after deploys if timestamps are not validated. Confirm production host separately from XAMPP.

Verification

php -i | findstr opcache. Repeat a PHP page with and without OPcache.

SQL-003 — Timesheet uniqueness check uses DATE(checkin)

Medium Priority: P2

CategorySQL sargability / N+1 writes
Affected Areatimesheet.php holiday-timesheet-ajax

Evidence

For each employee × date the code loads the employee name, then where_raw('DATE(`checkin`) = ?'), then loads salary fields again.

Current Behavior

About 3 queries per employee per holiday row. DATE(checkin) cannot use a plain index on checkin.

Root Cause

Per-row existence check instead of a range predicate and prefetch.

Recommended Fix

Use checkin >= day AND checkin < day+1. Prefetch employees with where_in. Optionally add a generated date column + unique key.

Example Fix

->where_gte('checkin', $checkinDate)
->where_lt('checkin', date('Y-m-d', strtotime($checkinDate.' +1 day')))

Expected Improvement

Estimate: indexable lookups; fewer round trips on bulk holiday insert. Not measured.

Tradeoffs

Need a matching index (employee_id, checkin).

Verification

EXPLAIN the existence query. Time a bulk insert.

Medium Priority: P2

CategoryPagination

CategoryCaching
Affected Areaibilling_bootstrap.php, ORM.php config

API-001 — Cron WhatsApp notifications are sequential HTTP calls with no timeout

Medium Priority: P2

CategoryExternal API / cron
Affected Areacronjob.php complete_order_notification, wati_notifiation()

Evidence

Each matching invoice calls WATI via cURL. CURLOPT_TIMEOUT => 0 (wait forever). Loop is synchronous.

Current Behavior

A slow or hung WATI API blocks the cron for every remaining invoice.

Root Cause

Inline HTTP in a foreach with unbounded timeout.

Recommended Fix

Set a short timeout (5–10s). Continue on failure. Prefer a queue or WATI broadcast batch. Do not log secrets in reports or VCS.

Example Fix

CURLOPT_TIMEOUT => 10,
CURLOPT_CONNECTTIMEOUT => 5,

Expected Improvement

Prevents unbounded cron runtime. Not measured.

Tradeoffs

Some messages may need retry.

Verification

Run cron with a mock delay; confirm it skips after timeout.

13. Expected Improvements

The following are estimates, not measured before/after numbers:

  • Dashboard chart APIs: on the order of 80+ SUM queries removed per page load if grouped SQL is used.
  • GST reports: query count from proportional to invoices×items down to a handful of statements.
  • Invoice product modal: 2 queries per product removed; DOM no longer holds the full catalog.
  • Timesheet grids: memory bounded by page size instead of full history.
  • OPcache + gzip: typically the largest cheap win for PHP TTFB and transfer size on this stack; confirm on the real host.

Do not publish invented millisecond timings. Re-test after each change (section 14).

15. Limitations

  • No authenticated browser session, so TTFB, LCP, INP, CLS, and waterfalls were not measured.
  • MySQL was not profiled: no table sizes, no SHOW INDEX, no EXPLAIN, no slow query log.
  • Query counts are inferred from source (loops and explicit SUM calls), not from a live query log.
  • Expected improvements are labeled estimates only.
  • Local XAMPP config may not match production cPanel. Treat SERVER-001 as host-specific until production phpinfo is checked.
  • mPDF, Stripe, and compiled Smarty templates were not treated as application bottlenecks except where controllers instantiate them.

16. Conclusion

Alabaya already has solid server-side lists for invoices, contacts, and products. The remaining bottlenecks are classic iBilling-era patterns: computing reports in PHP with N+1 queries, building charts with one SUM per day, loading full catalogs into forms, and shipping a heavy global JS/CSS set. None of the reviewed issues were confirmed as a live outage (no Critical). Fixing dashboard aggregates, GST, the product modal, and timesheet totals should yield the largest database-side gains. Enable OPcache and compression on the real web host, then re-measure with a query log and one authenticated DevTools pass.
